# 视频制作 Agent 降成本 SOP

适用于这类流水线：规划 agent（导演）出分镜 → 用户确认 → 每个镜头在沙箱里由制作 agent 写画面代码、渲染 → 检查与返工 → 配音、合成。成本几乎全在大模型调用上。

做法是先建账、再动手，按收益大、质量风险小的顺序推进。每一刀都用同一份分镜对比，结果写进账本。每个数字都要标明来源：实测、拟合还是重算。真实案例（30 秒片约 $2 → $0.42，1 分钟片约 $1.65 → $0.65）见 [references/case-study.md](references/case-study.md)，下面各条的依据和数字都出自那里。

## 1. 建账：每次调用都能归到某部片子的某一步

先把计量做全，再谈优化；没有账本，后面每一步都只是猜。

- 每次模型调用落一行：调用点（规划 / 制作 / 检查 / 配音 / 资料）、片子与镜头编号、第几次尝试、输入、缓存写入（按 TTL 分开记）、缓存读、输出 token、回复里调了哪些工具、**按官方价算的成本**。
- 用量以响应里的 `usage` 为准。没回话就断开的调用要单独标出来，不能按预占额记账，否则账本会多出一截没有用量依据的花费。
- 字段和查询模板见 [references/metering.md](references/metering.md)。
- **补历史基线**：账本上线前的片子，用沙箱原始会话日志里每条回复的 `usage` 还原。先拿一部账本上线后的片子，比对日志算出的成本和账本，误差在一次调用以内，才能用这个方法算其余的片子。改造前的基线一旦缺失就补不回来，所以开工前先把它存下来。

**完成标准**：任取最近 10 部成片，都能列出「规划 / 制作首稿 / 返工（按原因）/ 检查 / 配音」各花了多少，加起来与该片总花费对得上；改造前至少有 10 部成片的基线。

## 2. 诊断：把成本拆成「固定开销 × 段数」+「按秒增长」

- 用成片秒数和镜头数分别对制作成本做线性拟合，比较两个 R²，高的那个就是成本的真正驱动。例如按镜头 R² 0.79、按秒只有 0.03，说明钱花在镜头数上，片长只是表象，最大的杠杆是镜头切法（3A）。
- 算四个比：每镜调用次数、每镜平均秒数、制作 token 成本里缓存写入 / 缓存读 / 输出各占多少、返工按打回原因各占多少。
- 查缓存：每个段会话第一次调用的 `cache_read` 应该约等于共用前缀的长度。读到 0 或只读到很短一截，说明跨段缓存没共享上。出现 1 小时 TTL 的写入，说明有请求没显式写 TTL；把这部分 token 按 5 分钟价重算一遍，就是修好后确定能省的钱。

**完成标准**：能说出花费最多的三项，每项都有数字和对应的调用证据。

## 3. 按顺序拉杠杆

从上往下做。每做一项回到第 4 步验证，确认没问题再做下一项。

### A. 摊薄每段的固定开销（通常收益最大）

每段会话都有一份与长度无关的固定成本：读说明、搭环境、首次缓存写入、检查。镜头切得越碎，这份钱付的次数越多。

- 规定每镜最短时长（如 15 秒），镜头数按片长封顶（如每 15 秒最多一镜）。保存分镜时做硬校验，不合格就退回重排，限定次数。
- 片长改为固定档位，不让用户任意填秒数。
- 规划 agent 产出的分镜示例也要按长镜头写，否则它会照着示例切碎。

### B. 程序性步骤由平台来做，模型只负责创作

模型每多跑一个步骤，就多一次带着全部上下文的调用。

- 平台事先搭好目录、跑风格的准备脚本，把草稿和这一段需要的上下文直接写进第一条消息。
- 给一个「写文件 + 渲染」合一的工具，渲染报错原样交回。段一交上去，会话就结束，结尾只回一行。
- 每个会话设工具调用上限和渲染次数上限。
- 逐字时间戳压缩后再给模型；能用运行时查询函数代替的，就不放进上下文。

### C. 缓存卫生（检查清单）

- 每个请求显式写 5 分钟 TTL。有的中转站在没写 TTL 时会把缓存升级成 1 小时，写入价从 1.25 倍涨到 2 倍。
- 系统提示保持不变。会变的上下文（任务、标题、分镜）放进消息末尾，变了才追加。
- 各段共用的说明放在**逐字相同**的第一条消息最前面，只在共用块上打断点；本段专属的说明放在后面，或者改成由工具读取。
- 先放第一段，等它开始回复（共享前缀已写进缓存），再放其余段。
- 经过多账号中转时，给同一部片子的请求带会话亲和标识，固定落到一个账号上（缓存按账号隔离）。
- 中转站可能限制断点数量（例如最多 4 个，多出来的从最靠前的删起），这会让共用块的断点被删掉，要按限制来排布断点。
- 检查这类很小的调用也要打断点，否则会整条请求按 1 小时写缓存。

### D. 规划 agent（导演）

- 硬限制事先写进提示：总旁白上限、每句字符上限（按语言换算成大致词数）、片长和镜头规则。写超了被打回，就要整份重写，代价是一次大输出。
- 分镜落地后这一轮直接结束，不再多花一次调用说「请确认」。
- 联网查资料交给便宜模型跑一个小循环，只交回简报和来源，搜索原文和截图不进规划 agent 的上下文。
- 输出上限要够写完最长的分镜。被截断后，要明确提示重写，不能悄悄失败。

### E. 检查与返工：先量清每类返工的价值，再决定砍哪类

- 检查由系统来跑：布局自检和画面是否在动用程序测，不花模型调用；看图检查用一次很小的调用，只看缩略图。
- 自检要一次报出全部问题，每条带改法，并分出「观众看得出坏了，必须修」和「建议，只打标」。返工轮数设上限。
- 检查调用的输出上限要包含思考 token，太小会截断，返回空回答就等于没查。
- 想砍某类返工，先抽样看返工前后两版，量出「不返工时严重毛病的比例」，换算成整片至少出一处严重毛病的概率，交给负责人拍板。按代价从小到大可以考虑：收紧误报规则 → 放宽过严的阈值 → 只对严重毛病返工 → 全部去掉。

### F. 止损：把注定失败的花费挡在前面

- 渲染时按已画帧数推算完成时刻，晚于截止就立刻停，并把量到的速度告诉制作 agent。机器慢时少开几段并发。
- 沙箱里跑不动的能力（例如重 3D 渲染）在入口就拒绝；做到一半失败的片子，钱照样花掉了。
- 平台原因导致的超时、重试不占用模型调用的重试次数。

### G. 最后才动模型和价格

- 换便宜模型要用同一份分镜对比画面信息量。案例里，便宜一档的模型制作成本低 63%（$1.05 → $0.39），但画面信息明显变少，没有采用。
- 售价倍数是定价问题，不是成本优化。要和成本数字分开汇报。

## 4. 验证每一刀

- **同一份分镜 A/B**：旧流程和新流程各出一遍，比较调用次数、官方价成本、耗时，并逐帧看画面。这是唯一能把某一项改动单独拎出来的办法，要在改动上线前趁旧流程还在时做。
- **同片长档对比**：改造前后各取同一档片长的若干部实测，比较整片成本。不同档之间不要互相外推；某一档改造前没有样本，就如实写「没做过」，不拿拟合结果冒充实测。
- **对所有风格都生效**：优化放在平台层（任务说明、工具、测量、检查、风格合同和验收规则），不给单个风格打补丁。
- **质量底线**：不能出现明显瑕疵（大色块盖住主体、标题压字、文字被裁），画面要跟着旁白动。凡是改了模型看到的内容，都要再量一次「画面在动的时间比例」。
- **上线后复测**：随机抽 ≥5 个风格 × 全部时长档位，真实出片，重做第 2 步的拟合，与改造前对比。

**完成标准**：每项改动都有前后两组数字（成本、调用次数、质量指标）。质量指标退步的改动，要么补平台层的检查，要么回退。

## 5. 记账本

把每次测量写成一份存档：测法、明细表、结论，以及「去掉某项会怎样」的代价分析。负责人拒绝的省法要连同理由一起记下，免得后来的人重复提。

## 常见取舍

| 省法                 | 代价                                                             |
| -------------------- | ---------------------------------------------------------------- |
| 长镜头、镜头数封顶   | 剪辑节奏变粗；超短片做不了；样片和高光片要另行处理               |
| 一段只调一两次       | 模型不再自己探索，画面容易变静，要补「画面在动」的程序检查和退回 |
| 系统跑检查、封顶返工 | 封顶后剩下的毛病只能打标放行                                     |
| 单次调用做更多事     | 输出占比上升，每次调用变贵，但调用次数降得更多                   |
| 会话固定到一个账号   | 中转的负载均衡变差                                               |
| 固定时长档位         | 用户不能任意填时长；某些档位会撞上配音等下游服务的上限，要先查   |
